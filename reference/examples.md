### 4. 概述

**4.1 业务背景**

**业务场景：**
出于业务需要，用户会将最终产品的销售、物流、生产、采购等多流程文件上传到系统中进行线上管理，同时需提取文件中的关键信息形成贯穿全供应链的、严谨勾稽的数据流及文件流，最终以文件包及数据表单的形式进行输出。

**行业特点：**
硅材供应链主要包含组件、电池、硅片、硅棒、多晶硅、硅粉、工业硅、硅矿八大工段。包含外协、代工、直采等多种不同场景，不同场景对应的文件及数据串联关系均有不同，甚至同样工段根据代工客户不同也可能产生区别。

**当前痛点：**
目前文件类型缺乏统一管理，不同业务人员上传文件时分类标准不一致，导致后续文件查询和关联困难。文件关键信息提取规则不明确，无法形成有效的数据勾稽关系。

**解决方向：**
通过文件类型配置功能，统一管理系统中所有文件类型的定义，明确文件分类规则和关键字段，为后续文件上传、链路配置等功能提供标准化的数据基础。

**4.2 开发目的**

1. 进行文件类型及文件关键信息的定义，为文件类型提供统一管理界面及功能
2. 为后续其他功能如链路配置提供信息来源

### 5. 总体设计

**5.1 功能总体（流程）说明**

**【功能总体说明】**
本功能用于定义系统中进行管理的文件类型、文件类型分类及文件类型分类关键字段及默认实体信息。相关信息将用于后续文件上传及其他配置功能使用。

**【流程说明】**
1. 当出现需要进行管理的新文件类型时，相应责任人在界面中对文件类型进行配置
2. 当原有文件类型出现调整时，相应责任人在界面中对文件类型信息进行调整
3. 当原有文件类型不再使用时，相应责任人在界面中对文件类型进行失效

**【概念说明】**
- 【文件类型】是根据未来需从系统中输出文件的类型
- 【分类要素】是文件类型下区分小类实际文件的依据
- 【要素值】是实际中文件的类型
- 【关键字段】指实际文件中需要在系统中进行记录的信息
- 【实体】指数据管理过程中涉及的公司、客户、供应商等

> 以硅片代工合同为例：
> 未来系统需输出的文件维度为E9 Wafer Tolling Contract，硅片代工合同。这类文件对应实际中的两种文件，原始代工合同与补充合同。
> 那么在系统中体现为文件类型【硅片代工合同】下存在要素类型【合同类型】，该要素类型下存在两类要素值【原始合同】与【补充合同】，【原始合同】要素下关键字段为【合同号】、【合同数量】，【补充合同】要素下关键字段为【原始合同号】、【补充合同号】、【原始合同数量】、【补充合同数量】

## 示例二：业务背景四段式（简化版）

### 4.1 业务背景

**业务场景：**
出于质量合规要求，企业需要对所有出货产品进行追溯管理。当发生质量问题时，能够在规定时间内（如4小时内）完成从成品到原材料的全链路追溯，并出具影响范围报告。

**行业特点：**
医疗器械行业受FDA/CE/CFDA等多重监管，要求建立完整的器械历史记录（DHR），包括：原材料批次、生产工单、检验记录、灭菌批次、出货信息等。任何环节缺失都可能导致产品无法上市或面临召回。

**当前痛点：**
目前追溯信息分散在ERP、MES、LIMS等多个系统中，查询需要跨系统人工核对，平均追溯耗时2-3天。在2023年的模拟召回演练中，因数据断点导致20%的产品无法完成追溯，存在重大合规风险。

**解决方向：**
建立统一的追溯数据管理平台，通过数据集成和关联分析，实现一键式全链路追溯，目标将追溯时间从2-3天缩短至4小时以内，追溯覆盖率从80%提升至99%以上。

### 批次号字段设计

| 属性 | 值 |
|------|-----|
| 字段名 | 生产批次号 |
| 控件类型 | 文本 |
| 数值类型 | 字符 |
| 长度 | 20 |
| 必填 | 是 |
| 值列表来源 | 手工录入（部分场景支持扫码） |
| 级联关系 | 选择批次号后，自动带出：产品编码、产品名称、生产日期、有效期 |
| 默认规则 | 空 |
| 展示要求 | 显示完整批次号 |
| 支持搜索 | 是，支持模糊搜索 |

**校验规则：**
- 时机：保存时
- 条件：必须符合批次编码规则（产品代码+年月日+流水号）
- 报错："[生产批次号]格式错误，应为产品代码(4位)+年月日(6位)+流水号(3位)，如P001240315001"

**其他说明：**
- 支持扫码枪扫描条码自动填充
- 批次号在系统中全局唯一
- 失效批次号不可用于新增业务，但保留历史记录
